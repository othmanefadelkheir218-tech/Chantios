## Things to know before coding

- **Every `id` is a `SERIAL`** (auto-increment integer — changed from UUID on 2026-10-05, at the user's request, see `doc/notes/entity-fields.md`), and every `updated_at` defaults to `now()`. Raw SQL inserts work without supplying either.
- **`:id` / `:tenantId` path params are validated with `ParseIntPipe`**, not `ParseUUIDPipe`. A bad id gives `400` `Validation failed (numeric string is expected)`, not a UUID-specific message.
- **Line totals** (`quote_lines.total_excl_vat`, `invoice_lines.total_excl_vat`) are set by a trigger. Never compute them in the app; never send them.
- **Views are not Prisma models.** Read `material_stock_live`, `invoice_balance`, `project_margin_live` with `$queryRaw` and **pass `tenant_id` by hand** — the tenant extension cannot see inside raw SQL.
- **The API speaks snake_case** (`legal_name`, `base_price`). Prisma speaks camelCase. Each controller has `SnakeCaseInterceptor`; a handler turns a DTO into Prisma data with `toCamelKeys()`. Details in `00-START-HERE.md` § 6.
- **Money is a string in and out.** A response that carries a Prisma `Decimal` serialises it as a string already.
- **Swagger uses the `@nestjs/swagger` plugin** (`nest-cli.json`): `*.dto.ts` and `*.entity.ts` properties are documented automatically, with their doc comments.
- **Posting an analytics event:** inject `AnalyticsService` and call `track({ tenantId, userId, eventName, payload })`. It returns at once and never throws.
- **Step 14 / renewal job:** call `SubscriptionsService.snapshotUsage({ tenantId, periodStart, periodEnd, usage })`. **Step 02 registration** (built): `register-tenant.handler.ts` calls `PlansService.findDefault()` + `TenantsService.create()` + `UsersService.create()` + `SubscriptionsService.create()`, all inside one `prisma.$transaction()`.
- **Skip list for the tenant extension** (built, step 02): only `tenants`, `admin_users`, `plans`, `plan_features`, `stripe_events`, `roles`, `refresh_tokens`, `one_time_codes` — everything else goes through `TenantPrismaService` (`.db`), not the raw `PrismaService`. A repository method that's intentionally unscoped (`findByEmail`, `findByIdUnscoped`, anything inside a registration `tx`) says so in a comment — see Decisions below for the scalar-FK rule that goes with it.
- **New module, same shape as `audit`/`email`**: `src/sessions/` owns `refresh_tokens` (`SessionsService`) so `auth`, `users`, and the still-pending step 01 session-revoke TODOs can all reach it without a circular import.
- Docker project name: containers were once created under project `app`; they are now under `chantieros`. Volumes `app_*` are unused leftovers.

## Decisions taken during the build

- **2026-10-05 — step 02 structural decisions**, made autonomously while building (no acceptance test or explicit doc line rode on most of these; recorded here so they're not re-derived or second-guessed later):
  - **`refresh_tokens` lives in its own leaf module, `src/sessions/`**, not inside `auth/repositories/` as the step file's file tree literally shows. Reason: `deactivate-user.handler.ts` (users), the still-pending `set-tenant-status.handler.ts` (tenants) and `deactivate-admin-user.handler.ts` (admin-users) all need to revoke sessions too, and `auth` already needs to import `users`/`admin-users` — importing back would cycle. Same fix already used for `src/stripe/` in step 01; documented there as precedent.
  - **Prisma `create()` through the tenant-scoped client requires scalar FKs everywhere on that row, not relation `connect`.** The extension injects `tenantId` as a plain scalar (required — `createMany` can't do relation connects at all); mixing that with even one `{ connect: { id } }` elsewhere in the same payload makes Prisma demand the `tenant` relation too and throw `Argument "tenant" is missing`. Hit this live in both `register-tenant.handler.ts` (fixed by using full relational style there instead, since it runs on a raw `$transaction` client, not the extension) and `accept-invitation.handler.ts` (fixed by switching to `roleId: x` instead of `role: { connect }`). Rule is written as a comment directly in `tenant-extension.ts`.
  - **`UserRepository` needs two different "by id" reads**: `findById` (tenant-scoped, for an authenticated admin reading their own team) and `findByIdUnscoped` (raw, for `refresh`/`change-password`, which resolve the id from a JWT before — or entirely without — a tenant in `nestjs-cls`). Mixing these up throws the same "no tenant in context" error `findByEmail` was already written to avoid.
  - **Transactional cross-module writes use an additive, optional `tx?: Prisma.TransactionClient` parameter**, threaded through exactly the methods `register-tenant.handler.ts` needs: `TenantRepository.create/findByEmail` → `CreateTenantHandler` → `TenantsService.create`, `UserRepository.create` → `UsersService.create`, `SubscriptionRepository.create` → `CreateSubscriptionHandler` → `SubscriptionsService.create`, and `AuditRepository.write` → `WriteAuditLogHandler` → `AuditService.write` (so the tenant-creation audit entry rolls back with everything else). Every existing call site omits the param and is unaffected — verified by re-running the full step 01 suite (92 tests, unchanged) after these edits.
  - **Admin 2FA**: `one_time_codes` is not used for the `admin_2fa` challenge's own attempt/lockout tracking — TOTP (otplib) is verified directly against `admin_users.totp_secret`, independent of any stored hash, so running it through `OneTimeCodesService.verify()`'s hash comparison would falsely fail every correct code. Instead, `admin-login.handler.ts` issues a short-lived (5 min) signed JWT "challenge token" naming the admin; `verify-2fa.handler.ts` decodes it and checks the TOTP directly. No `one_time_codes` row is written for this type at all yet. No enrollment route exists either — see *Blockers*.
  - **The registering user's own email verification (`users.email_verified_at`) reuses `OneTimeCodesService`/`EmailService` directly** in `register-tenant.handler.ts`, not `TenantsService.sendVerificationEmailTo()` — that step 01 method targets `tenants.email_verified_at` (the super-admin-created-tenant path) and is a different column on a different table.
  - **Jest config needed `transformIgnorePatterns`** (both `package.json`'s `jest` key and `test/jest-e2e.json`) to let `otplib`/`@otplib`/`@scure`/`@noble` through — otplib v13's internals are ESM-only and Jest's default ignores all of `node_modules`.
- `id` and `updated_at` get database defaults, so raw SQL works. (Prisma's client-side `uuid()` alone left raw inserts failing — moot now that `id` is `SERIAL`.)
