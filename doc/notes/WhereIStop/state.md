## Things to know before coding

- **Every `id` is a `SERIAL`** (auto-increment integer — changed from UUID on 2026-10-05, at the user's request, see `doc/notes/entity-fields.md`), and every `updated_at` defaults to `now()`. Raw SQL inserts work without supplying either.
- **`:id` / `:tenantId` path params are validated with `ParseIntPipe`**, not `ParseUUIDPipe`. A bad id gives `400` `Validation failed (numeric string is expected)`, not a UUID-specific message.
- **Line totals** (`quote_lines.total_excl_vat`, `invoice_lines.total_excl_vat`) are set by a trigger. Never compute them in the app; never send them.
- **Views are not Prisma models.** Read `material_stock_live`, `invoice_balance`, `project_margin_live` with `$queryRaw` and **pass `tenant_id` by hand** — the tenant extension cannot see inside raw SQL.
- **The API speaks snake_case** (`legal_name`, `base_price`). Prisma speaks camelCase. Each controller has `SnakeCaseInterceptor`; a handler turns a DTO into Prisma data with `toCamelKeys()`. Details in `00-START-HERE.md` § 6.
- **Money is a string in and out.** A response that carries a Prisma `Decimal` serialises it as a string already.
- **Swagger uses the `@nestjs/swagger` plugin** (`nest-cli.json`): `*.dto.ts` and `*.entity.ts` properties are documented automatically, with their doc comments.
- **Posting an analytics event:** inject `AnalyticsService` and call `track({ tenantId, userId, eventName, payload })`. It returns at once and never throws.
- **Step 14 / renewal job:** call `SubscriptionsService.snapshotUsage({ tenantId, periodStart, periodEnd, usage })`. **Step 02 registration** (built): `register-tenant.handler.ts` calls `PlansService.findDefault()` + `TenantsService.create()` + `UsersService.create()` + `SubscriptionsService.create()`, all inside one `prisma.$transaction()`.
- **Skip list for the tenant extension** (built, step 02): only `tenants`, `admin_users`, `plans`, `plan_features`, `stripe_events`, `roles`, `refresh_tokens`, `one_time_codes` — everything else goes through `TenantPrismaService` (`.db`), not the raw `PrismaService`. A repository method that's intentionally unscoped (`findByEmail`, `findByIdUnscoped`, anything inside a registration `tx`) says so in a comment — see Decisions below for the scalar-FK rule that goes with it.
- **New module, same shape as `audit`/`email`**: `src/sessions/` owns `refresh_tokens` (`SessionsService`) so `auth`, `users`, and the still-pending step 01 session-revoke TODOs can all reach it without a circular import.

## Decisions taken during the build

- **2026-10-06 — step 06 structural decisions**:
  - **`TenantTransactionClient` added to `tenant-prisma.service.ts`** — the type of `tx` inside `this.tenantPrisma.db.$transaction(async (tx) => {...})`, extracted via `Parameters<Parameters<TenantScopedClient['$transaction']>[0]>[0]` rather than typed as the raw `Prisma.TransactionClient`. Needed because a Prisma Client Extension's `$transaction` produces a structurally different (if runtime-compatible) generic shape — typing it as `Prisma.TransactionClient` is a real compile error here ("not callable"/excessive stack depth), not a style choice. Every repository method threading `tx` across a cross-module transaction from here on should reuse this exported type, not re-derive it or fall back to `Prisma.TransactionClient`.
  - **`accept-quote.handler.ts`'s transaction opens on `this.tenantPrisma.db.$transaction(...)`, not the raw `PrismaService`** — unlike step 02's `register-tenant.handler.ts` (which runs before any tenant exists), a tenant context already exists during quote acceptance, so the tenant-scoped client is the correct one to transact on.
  - **`StartProgressFromQuoteHandler` (new, `src/projects/handlers/`) is a narrow second path into `projects`, not a reuse of `ChangeStatusHandler`** — the latter's admin-only-reopen check has no meaning for quote acceptance, and quote acceptance isn't an HTTP status-change route. It still reuses `canTransition` from `project-status.helper.ts` (never re-implements the matrix) and is a no-op (no write, no history row) when the project is already `in_progress` — the matrix has no self-transition, and a second accepted quote on the same project must not look like a second real transition.
  - **`AuditService.write()` is never passed `tx`, anywhere in this step** — matches the existing codebase convention (`set-recipe.handler.ts`, `create-project.handler.ts`): the audit row is a best-effort side write after the business transaction commits. Also avoids a second, separate type mismatch (`AuditService.write(entry, tx)` is typed to the raw `Prisma.TransactionClient` elsewhere, not `TenantTransactionClient`).
  - **Per-line `vat_rate` is trusted from the DTO as sent, never recomputed/overridden server-side** from `services.default_vat_rate` — only the document-level `default_vat_rate` (the new-line pre-fill) is copied from the tenant at creation. `entity-fields.md`'s "pre-filled by the client" is read as the frontend's job.
  - **A genuinely new, not-invented gap found during review, flagged rather than silently fixed**: `payments.amount` carries a DB `CHECK (amount > 0)` (`doc/Schema Proposal.md` § 6), which makes the already-decided Overpayment rule's "a negative correction... naturally reopens `paid → partially_paid`" structurally unreachable as built — `amount_paid` can only increase under the real constraint, so `balance_due` can only fall. Added as open question 9 to both `A_progress-tracker.md` and `Schema Proposal.md`. Not resolved — needs a decision (relax the CHECK via a migration, or rewrite the rule) before anyone relies on it.
  - **Build delegated inside an isolated git worktree this time** (`isolation: "worktree"`) rather than directly in the main checkout (steps 03–05's pattern) — meant reviewing the agent's diff in the worktree, hand-copying the changed/new files into the main checkout (not a git merge — nothing to merge, just files to carry over, since the worktree's changes were uncommitted), then re-running the full verification suite a second time against the main checkout's real DB before trusting it, then removing the worktree. No problems resulted, but it's an extra manual step worth planning for if a future delegation also uses worktree isolation.
- **2026-10-06 — step 05 structural decisions**:
  - **`categories`' shared-defaults guard is structural, not just a handler check**: reads use the raw `PrismaService` with an explicit `OR: [{tenantId: null}, {tenantId}]`; writes (`update`/`archive`) go through the **tenant-scoped** client instead, whose extension auto-injects `tenant_id` into the `WHERE` — a `NULL`-tenant row or another tenant's row simply never matches, so editing one always 404s by construction, not by a remembered `if` check.
  - **`@IsNumberString()` cannot be combined with `@Min()`/`@Max()`** in this `class-validator` version (`Min` requires the value to already be a `number`, but every quantity/price field must stay a `string` for Prisma's `Decimal` columns). Every DTO in this step validates format only; the actual bound (positive, non-negative, non-zero) is a handler-level check instead (`assertPositiveQuantity`, `assertNonZeroQuantity`, etc.). Same reasoning likely applies to any future DTO with a `Decimal`-backed numeric field — don't re-discover this.
  - **`recipe.helper.ts`'s `RecipeLine` shape is `{ serviceId, quantity }`**, invented for this step since no quotes module exists yet to dictate the real shape. Step 06 must map its actual `quote_lines` data onto this interface at the call site; the recipe walk itself (`walkRecipe`) should not need to change.
  - **`release-reservations` closes one of step 04's 4 `// TODO` markers for real** — `ProjectsModule` now imports `StockModule`, `cancel-project.handler.ts` calls `StockService.releaseByProject()`. The other 3 (quote auto-switch, cancellation alert, closure snapshot) stay as `// TODO: step NN` until their step is built.
  - **A flaky unit test found and fixed**: `materials.handlers.spec.ts`'s `material()` fixture called `new Date()` per invocation; the one test that built it twice and deep-equality-compared the results failed ~1 run in 6.
