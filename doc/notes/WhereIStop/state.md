## Things to know before coding

- **Every `id` is a `SERIAL`** (auto-increment integer — changed from UUID on 2026-10-05, at the user's request, see `doc/notes/entity-fields.md`), and every `updated_at` defaults to `now()`. Raw SQL inserts work without supplying either.
- **`:id` / `:tenantId` path params are validated with `ParseIntPipe`**, not `ParseUUIDPipe`. A bad id gives `400` `Validation failed (numeric string is expected)`, not a UUID-specific message.
- **Line totals** (`quote_lines.total_excl_vat`, `invoice_lines.total_excl_vat`) are set by a trigger. Never compute them in the app; never send them.
- **Views are not Prisma models.** Read `material_stock_live`, `invoice_balance`, `project_margin_live` with `$queryRaw` and **pass `tenant_id` by hand** — the tenant extension cannot see inside raw SQL.
- **The API speaks snake_case** (`legal_name`, `base_price`). Prisma speaks camelCase. Each controller has `SnakeCaseInterceptor`; a handler turns a DTO into Prisma data with `toCamelKeys()`. Details in `00-START-HERE.md` § 6.
- **Money is a string in and out.** A response that carries a Prisma `Decimal` serialises it as a string already.
- **Swagger uses the `@nestjs/swagger` plugin** (`nest-cli.json`): `*.dto.ts` and `*.entity.ts` properties are documented automatically, with their doc comments.

## Decisions taken during the build

- **2026-10-06 — step 06 structural decisions**:
  - **`TenantTransactionClient` added to `tenant-prisma.service.ts`** — the type of `tx` inside `this.tenantPrisma.db.$transaction(async (tx) => {...})`, extracted via `Parameters<Parameters<TenantScopedClient['$transaction']>[0]>[0]` rather than typed as the raw `Prisma.TransactionClient`. Needed because a Prisma Client Extension's `$transaction` produces a structurally different (if runtime-compatible) generic shape — typing it as `Prisma.TransactionClient` is a real compile error here ("not callable"/excessive stack depth), not a style choice. Every repository method threading `tx` across a cross-module transaction from here on should reuse this exported type, not re-derive it or fall back to `Prisma.TransactionClient`.
  - **`accept-quote.handler.ts`'s transaction opens on `this.tenantPrisma.db.$transaction(...)`, not the raw `PrismaService`** — unlike step 02's `register-tenant.handler.ts` (which runs before any tenant exists), a tenant context already exists during quote acceptance, so the tenant-scoped client is the correct one to transact on.
  - **`StartProgressFromQuoteHandler` (new, `src/projects/handlers/`) is a narrow second path into `projects`, not a reuse of `ChangeStatusHandler`** — the latter's admin-only-reopen check has no meaning for quote acceptance, and quote acceptance isn't an HTTP status-change route.   - **`AuditService.write()` is never passed `tx`, anywhere in this step** — matches the existing codebase convention (`set-recipe.handler.ts`, `create-project.handler.ts`): the audit row is a best-effort side write after the business transaction commits. Also avoids a second, separate type mismatch (`AuditService.write(entry, tx)` is typed to the raw `Prisma.TransactionClient` elsewhere, not `TenantTransactionClient`).
  - **Per-line `vat_rate` is trusted from the DTO as sent, never recomputed/overridden server-side** from `services.default_vat_rate` — only the document-level `default_vat_rate` (the new-line pre-fill) is copied from the tenant at creation. `entity-fields.md`'s "pre-filled by the client" is read as the frontend's job.
